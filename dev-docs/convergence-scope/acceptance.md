## 缺陷

原 `HARD_READ_ONLY_RE` 把不限定对象的"不要修改/不得修改/do not modify"一律视为整轮只读，`hardReadOnly || researchOnly` 又压倒执行意图。复现：`修复薪资导入代码，不要修改生产数据。` 得到 `readOnly=true, executionIntent=false, hints=0`，常见授权任务因此绕开收敛检查。

## 修复语义

在 `applyTurnText` 中改为按用户指令文本分类：

1. **先去掉引号与代码块内容**：`"请勿修改生产数据"`、`` `do not modify` ``、围栏代码中的否定句属于被讨论的材料，不是本轮指令。ASCII 单引号不清除，避免吞掉 `don't`。
2. **整轮只读标记**：`只读`/`read-only` 作为任务类型；对象属性描述不算，包括 `只读文件/目录/属性/权限/挂载`、`只读副本/实例/节点/标志/配置/模式`、`read-only replicas/flag/mode`、"设为/改成/标记为只读"，以及 `该目录只读`、`database is read-only` 这类主语是对象的事实句。`任务是只读的` 仍按任务类型处理。
3. **整轮只读禁令**：`不要/禁止/不得/别/do not...` 后无对象，或对象是泛化代码目标（代码/源码/文件/任何文件/实现/codebase 等）→ 整轮只读。"不要动手改代码"同样归入整轮。对象明确但不属于任何受限范围、且全文没有其他执行请求时（`不得修改接口`、`不要修改业务逻辑`、`不要修改它`）也按整轮只读，防止助手表态突破用户禁止编辑。
4. **对象受限禁令**：对象是生产数据、数据库、凭据、账号、配置、环境、其他文件/模块、`outside/except/other` 限定的目录等 → 只约束副作用，不标记整轮只读；泛化对象再被限定（`any files in production/`、`the code path that writes to production`、`代码里的生产环境配置`）同样按受限对象处理。对象从句以标点或 `并/然后/but/and` 等分句边界截断，避免把下一句当对象。
5. **引号对象**：引号/代码块内容替换为占位符而不是删除，`do not modify "production data"`、`不要修改「生产数据」` 仍保留受限对象，不会退化成整轮只读。
6. **执行/研究意图**在移除禁令从句后判断，避免"只分析，不要修改生产数据"因禁令中的"修改"被当成执行请求；裸 `不修改` 仅在分句起始处视为禁令（`不修改订单模块，只修改支付模块`），句中描述性的"重复读取但不改代码"和"不得不修改"不算。
7. **仅分析/仅给方案**：`只给方案`、`仅提供分析`、`只做评审` 等保持整轮只读。
8. 助手表态（"开始修改代码"）只影响阶段计数，不改变用户的只读范围。

歧义处理：无法确定对象范围时偏向整轮只读（宁可少提示，不误判用户禁止编辑）；对象明确受限时按执行任务处理。边界均写在源码注释中。

## 本轮输入检查

`applyTurnText` 的 `turnText` 来自 `getCurrentTurnSourceItem()?.messageText`，即 `enqueueUserMessage` 收到的完整文本（external CLI / inbox / Task 会把调用方说明与约束一起带入），不是另行拼装的隐藏系统提示。因此检测只统计文本中明确的指令，并且按禁令对象分类；调用方包装说明里的"不改账号权限/配置"这类受限约束不会把任务误判为只读。
