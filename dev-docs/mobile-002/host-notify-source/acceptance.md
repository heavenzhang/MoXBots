## Owner and contract

- The existing Node Host supervisor observes only its current original worker generation/session terminal callback and a bounded read-only original `state` projection for pending interactive requests. Source polling cannot create/start/send/respond/stop a Session. The projection runs outside the IPC dispatcher; its child RPC timeout is 1 second and at most one observation is pending.
- A pointer must have exactly one enabled, nonarchived Agent registration for the original SessionStore workspace. Existing `resolveRemoteAgent`/ordinary-Agent delegation guard and `remoteSessions.validateSession` recheck SessionStore visibility, workspace and private Bot exclusions before persistence and every dequeue. Each original Active worker captures its verified local source authority at birth. True InternalAuthority admission can establish that authority before worker creation. Async observations explicitly carry the birth scope and recheck it inside the queue and before disk write; a later account peek cannot rebind an existing worker. Worker generation/session identity/current supervisor object, Bot/bootstrap and shutdown guards apply at origin.
- Colocated `local-source-request/response` is a closed, separate envelope with current local DeviceScope, original connection scope and account/management binding. It has no controller/phone peer and adds no public management operation. It uses the existing protected reverse Unix socket, existing connection mutex and UID guard. The mutex is released before HTTPS.
- `POST /api/mobile-notify/v1/source/challenges` requires exact HTTP **201**; body `{version:1,sourceEventId,connectionEpoch,agentId,sessionId}`. Rust rereads the existing owned credential owner, validates the captured account/management binding, obtains the challenge, rereads the origin pointer, and signs using the original native `DevicePrivateKey.sign_proof`. `expiresAt` is Unix seconds. `POST /api/mobile-notify/v1/source/hints` requires exact HTTP **200** and a canonical event UUID before a local ACK. Both routes reuse the pinned OwnedClient, strict no-store JSON, 8KiB limits, no redirects and no HTTP retries.
- Uncertainty/expired challenge requests a new challenge with the original durable source ID/epoch/exact pointer. A retry publishes only a generic hint. No Session command retry is introduced. Same-device generation/account/binding changes select another outbox scope; old events are never relabeled/rebound.
- The publisher is a future inside the original socket select and is dropped on disconnect/shutdown. It runs only for an owned connection with the existing explicit management runtime/grant and after Ready. Repeated failure sleeps up to 60 seconds. There is no second socket, peer sequence or credit owner.

## Durability and privacy

`<existing Host stateDir>/mobile-notify-source-v1/<SHA256(full local scope+account/management bindings)>.json`, private directory0700/file0600, no symlink reads, bounded128 pending entries plus128 durable deferred entries,512 compact confirmed observation-hash tombstones,512KiB maximum read/24h TTL. ACK removes pending entries and promotes deferred entries; confirmed tombstones do not consume pending capacity. Full256 unconfirmed capacity raises SOURCE_CAPACITY and emits only a safe unconfirmed diagnostic; no completion is invented. Atomic temp write+fsync+rename+directory fsync+readback precede export and ACK. A confirmed ACK is durably marked; lost ACK response and restart retain the original source ID/epoch and dedupe observation. Stored fields are pointers, worker generation, observation ID, creation time and confirmed opaque event ID. No titles, text, filenames, approval choices, Bearer or keys are included.

Before the first authenticated source IPC initializes an account scope, a terminal observation is conservatively ignored rather than assigned to a future account. Native process/HTTP/device cancellation, DeviceStore generation drift and end-to-end original Host/account boundaries still require combined acceptance. TTL/capacity intentionally bound delivery; this queue does not claim exhaustive notification history.
