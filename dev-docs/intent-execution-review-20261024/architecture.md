## 结论与范围

建议把 MoXBots 收敛成一条闭环：**理解用户要什么 → 核对已有授权 → 明确可验收结果 → 选择执行方式及模型 → 执行并记录证据 → 验收或返工 → 在原 owner 下继续或停止。** 多模型是完成任务的手段，多 Agent 是有条件的执行方式，三档难度都不能代替这条闭环。

完整机制不需要另一套 ExecutionContract 数据库、全局自主 Agent 平台或第二个 scheduler。已有方案内容可承载目标、范围、步骤和验收标准；已有任务账本承载尝试、关联和验收；原用户输入与 Task/Goal owner 提供授权依据；SessionEngine/native queue 拥有准入和执行；Query/bridge 拥有一次推理恢复和动作保护。应补齐这些入口之间的确定性检查，并收敛为一套模型策略。[S01–S12]

明确“把课程体系做成网站”已经表达了制作意图。应在原授权范围内查材料、制作并验证网站，不因涉及多步骤就机械要求用户再点一次方案确认。公网发布、付费或新增敏感权限等未获授权的动作单独停在相应边界，网站制作本身继续。用户明确“先出方案，等我确认”则只交方案。这里是**建议的产品规则**；当前实现及迁移限制见后文，不能用此建议绕过现有待确认方案。

## 二、把四个决定分开，放在同一次准入中

下面全部为建议，不代表当前实现。

| 决定 | 它回答的问题 | 输入及权威 | 不能做什么 |
|---|---|---|---|
| 意图 | 用户是在问、要方案、要求做事，还是纠正/控制当前工作？ | 真实用户输入、当前任务上下文；模型可提取结构化建议 | 不能凭“strong”“是问句”或一个 confidence 数字授予行动权 |
| 授权 | 这些具体行动是否落在已有授权内？ | 可信入口、人类回执、原 Task/Goal owner、现有工具权限 | 模型提取、文档内容、工具输出不创造授权；用户允许制作不自动授权付费/公网发布 |
| 执行方式 | 直接回答、一个 Agent，还是多个独立工作包？ | 可验收产物、依赖、资源互斥、Runtime 能力、成本 | 不把复杂、迟迟无输出或模型故障直接映射成多 Agent |
| 验收 | 当前成果是否达到用户要求？ | 与当前任务/attempt/产物绑定的检查结果 | final 文本、进程 idle、HTTP 200 或子 Agent 自报不直接等于完成 |

这些决定可以共享原 turn 准备过程，但不能塞进“分类器输出 1/2/3”一次裁决。分类结果只是模型选择的一个软输入，权限约束由原 owner 在最后派发边界强制检查。

### 意图与行动决策表

| 用户输入与上下文 | 立即执行 | 等待条件 |
|---|---|---|
| “这套课程体系有哪些问题？” | 分析，必要时只读查证；直接回答 | 缺材料才做针对性澄清，不创建建站任务 |
| “先讨论网站方案，别开发” | 输出可审阅方案 | 不进入制作；只读检查不扩大范围 |
| “把课程体系做成网站”/“能不能帮我把它做成网站” | 识别为行动请求；利用已给材料制作，可逆细节自行判断；记录可验收结果 | 仅在实质范围缺口、外部后果或用户明确要求先审时等决定 |
| “按这个方案做” | 绑定用户实际看过的方案/版本；已有同版确认不重复要求 | 不明确指向、带新增限制或旧版本时不猜测为全量批准 |
| “继续” | 延续已核对的原任务、权限、停止原因与进度 | 不解除安全 stop、未知写入或预算上限；无可定位任务时先定位 |
| “颜色改蓝色，其他照旧” | 对原目标做局部修订，重新验收受影响部分 | 不把纠正当另一个竞争执行者；不重做已确认无关成果 |
| “暂停/停止”或撤回动作权限 | 原 owner 同步撤销后续准入并精确停当前工作 | 终止不确定需对账；迟到输出不复活工作 |

“有计划”与“要审批”是两个轴。内部复杂计划可自动形成；人类决策卡仅在授权不足/用户要求审阅时出现。当前已进入 awaiting_confirmation 的历史方案保持原门禁，不因新策略上线被自动授权；实现新规则需显式版本迁移与兼容测试。[当前门禁依据 S08–S10]

### 最小字段，不建第二份合同

保留 `SessionTaskLedger` 作为方案、尝试、验收记录的现有容器。仅针对需要持久步骤的行动任务增量扩展；纯回答不为了凑账本创建任务。

| 信息 | 建议位置与最小增量 | 不复制的内容 |
|---|---|---|
| 目标、范围、总体验收、依赖图 | 继续使用现有 plan/proposal 的 objective、scope、acceptanceCriteria、steps/blockedBy | 不再存一份独立 ExecutionContract |
| 原始意图及授权来源 | 原 turn/message locator；方案保存绑定引用与 scope digest；由可信入口/原 owner 写入 `original_request` 或原 human confirmation 的授权依据 | 不把完整聊天、凭据、Task/Goal 状态复制进方案；模型不能自填可信授权 |
| 计划可执行与待人决策 | 在原方案 lifecycle 区分“原请求已授权”与“仍需确认”；保留旧明确确认 receipt | 不伪造用户点了确认，不用 confirmed 字样冒充发生过人类审阅 |

## 三、直接做还是组织多人：角色按工作需要出现

默认一个 accountable 主 Agent 负责结果。协调者、实现者、验证者是当前工作的职责，允许由同一 Agent 承担；使用多个模型也可只是串行咨询，不等于多个可写执行者。

| 情况 | 推荐方式 | 验收与说明 |
|---|---|---|
| 短问答、局部可逆修改、紧耦合问题 | 一个 Agent 直接处理 | 主 Agent 做相称检查；不为形式增加一个审阅调用 |
| 实现与验证连续依赖、同一文件密集修改 | 一个实现者串行推进；需要时追加审阅 | 先出可检查产物，再审阅；避免两人同时写同一区域 |
| 两个以上输入/输出明确、依赖已满足、资源可隔离的工作包 | 由原 Runtime 组织有限并行 | 每包明确 task ID、边界、验收、产物位置；主 Agent 集成验收 |
| 高影响变更、有可独立核对的证据 | 实现后由另一执行上下文审阅；可用时选另一模型 | 独立来自不同证据/检查路径，不能仅凭模型不同宣称独立正确 |
| 另一模型擅长分析但缺工具/权限 | 作为文本咨询/审阅建议 | 原实现者应用、运行和验收；咨询结果不显示“测试已通过” |
| 当前没有进展 | 先诊断等待模型、等工具、等审批、依赖未满足或反复读 | 病因是连接故障时换 Agent 不会修复；缺输入时盲目并行只复制阻塞 |

并行必须同时满足：任务有独立输出；已满足必要前置；写资源不重叠或有原生隔离；接口已约定；当前 Runtime 可证明支持准入/停止/结果关联；预算预留成功。满足不了就串行。单一任务始终只有一个当前有效 attempt；并行用明确子任务表达。[与现有 S11 保持一致]

工作包最小交接：目的和完成条件、输入版本、允许的工具/数据/路径、依赖、实际模型要求、预算份额、产物及检查证据。禁止用全量聊天压给每个子 Agent 后声称已经完成上下文管理。

第一版有工具的工作沿已支持的 native Agent 路径；不同 Provider 的咨询沿原 route assist。不得将“Provider A 协调、B 写文件、C 验收”作为现有能力承诺：任意跨 Provider 工具子任务的独立身份、history、取消和计费归属仍需实证。[S14–S15]

## 四、一个模型策略：先约束资格，再按证据选择

用户只维护同一个启用候选池与固定/自动选择、已有费用授权/上限。后台使用同一个纯策略决定初选、故障切换、能力升级、冷却与预算；不恢复“主模型一套配置、备用模型另一套配置”。三个档位可作为偏好和兼容显示，不能充当全部能力模型。

### 同一策略的输入与决策顺序

1. **硬资格**：池成员启用；分享/费用授权；本运行环境可执行；精确工具协议/媒体/上下文及输出预算满足；当前 history 可续接；权限与原任务未撤销。未知的关键能力不能按“强档”自动认定支持。
2. **服务健康**：区分配置就绪、近期真实调用成功、当前故障/冷却和未知。记录来源、时间和适用能力；简单文本成功只证明相应路径，不能证明工具或图片可用。优先被动利用已授权调用结果，不默认跑收费 benchmark/定时探测。
3. **任务适配**：根据工作包的实际要求和已验证表现选路。协调者需要可靠结构化计划/长程上下文；实现者需要工具及代码任务能力；验证者需要相应检查路径。三者无需固定命名模型，也不机械绑定 strong/fast。
4. **成本和延迟**：在前述合格集合中，按用户偏好、可追溯价格、实际 TTFT/总时长、可用性和缓存成本排序。没有实际数据就明确未知，不编造质量分或成功概率。初版可按确定性优先序实现，不急着引入带虚构权重的总分公式。
5. **冻结与重新决策边界**：一个当前 attempt 保持执行身份；在未交付安全重试、原 turn 的合法接管、已结算后的返工/新步骤等可证明边界重新决策。每次 await 后和 native entry 前复核授权/预算/配置，禁止中途任意换 Provider。

策略本身不保存第二份执行状态。catalog 继续给 desired 配置/声明能力，现有 auto-route 服务可维护有界的近期路由观察，Query/原 queue 执行决策，持久安全证据仍由 SessionStore/原 Task/Goal 写入。跨进程重启后缺失的临时健康数据显示“未知”，不将其恢复成“健康”。

### 故障域与选择要点

候选身份至少记录精确 Provider/model/API endpoint 路径类别、Runtime，以及可确认的故障域。共同网关、账号额度、上游或出口网络可能相关；两个不同名字或 Provider 配置不证明两个独立故障域。能确认的先按 endpoint/账号作用域分组，无法确认的相关性标 unknown，不伪造独立性。

| 事件 | 统一策略的建议动作 | 禁止动作 |
|---|---|---|
| 连接重置/5xx/headers timeout，尚未交付且原 lease 安全 | 有限短试；若同域持续失败，优先同能力且不同已知故障域候选；没有时才沿原 deadline 等待 | 反复把同网关的多个 alias 当独立可用路径，每换名字重开计时 |
| 429 速率限制 | 解析结构化类别及 Retry-After，按其真实作用域冷却，选择不共享限制的合格路由或等待 | 绕过明确等待时间；欠费/额度不足误当临时速率限制 |
| 认证、权限、欠费、模型不存在、参数错误 | 报告具体配置/权限原因；保留原成果，允许不受影响工作继续 | 用其他凭据/付费路线规避约束，或无限换模型掩盖错误 |
| 工具失败、测试失败、业务校验失败 | 修正工具/实现；必要时在原范围内返工 | 把每次工具错误算作 Provider 不健康 |
| 验收证明当前能力不足 | 当前 attempt 结算后，重新挑满足要求的模型/推理投入；增加可核对的检查 | 凭一段难看回答自动升价，或在未知写入时更换实现者重做 |
| 所有兼容候选不可用 | 给出已尝试事实、冷却/剩余窗口、可解除条件；可继续独立的非模型工作，否则有界等待或安全停 | fallback 到池外模型、削减历史/媒体、重放原指令 |

当前清理只允许同档故障接管，这是本批事实。[S05–S07] 未来“能力升级”应是同一策略依据要求选择更合适路线，不新增跨档开关；第一版保留当前同档规则，待能力与费用门禁具备后再扩展。传输故障的换路和验收失败的返工需要不同 reason、attempt 边界及预算记录。

### 预算及冷却

预算以原业务任务为父级，包含分类、协调、咨询、实现、验证、重试、返工。子调用先从父预算预留，结算后释放未用部分；不能复制整份额度。Query 的短重试、SDK 重发、故障接管、Goal 续轮共享相应原恢复链的绝对期限，不能互相续命。

第一阶段保留现有 30 分钟恢复上限作为兼容 ceiling；任务期限或用户上限更早则取更早者。[当前 30 分钟见 S07] 不把这 30 分钟当交互式任务必须用满的等待时间。应按已尝试故障域、剩余预算和独立可推进工作决定是否继续。

成本未知时显示 token/调用上限及估算依据；价格或最终 usage 不可靠时不能承诺精确金额硬封顶。必要时保守保留最大输出额度，不为超预算任务继续发新调用；用户另行提高上限才可增加额度。全局 cooldown 避免同域请求风暴，单任务等待仍归原 Query/Task/Goal，不新建后台重试器。

## 五、首个协调模型失败：控制逻辑必须先于模型

不需要另一位常驻“超级协调模型”才能启动任务。由原 SessionEngine 准备入口完成可确定的配置/权限/预算检查，保存原用户输入与任务引用，依据统一策略选中可用路线；语义理解和计划随后由模型完成。

| 首调阶段 | 继续方式 | 权限边界 |
|---|---|---|
| 可选难度分类未返回 | 有界结束分类；用已知任务要求/前档作保守路由，首次未知可采用池内合格默认协调路线 | 允许继续理解意图，不因分类失败增权或自动认定用户要写业务 |
| 主模型首个推理请求零交付失败，能证明原 lease 安全 | 原 Query 控制器在同一任务、同一预算内改用兼容候选，候选读取同一用户输入和已确认进度 | 不等待失败模型自己调用外援；不 enqueue 第二份用户任务；不制造子 Agent 完成记录 |
| 已有部分输出或任何工具可能执行 | 原 owner 检查 native terminal、action ledger、后台任务和 stream continuation 许可；可安全接续才继续 | 零可见文本也不能免核工具/外部副作用；不能直接从头重跑 |
| 候选也无输出或同故障域不可用 | 原控制器依据总预算及 Retry-After 等待/暂停，报告具体停因 | 不让新协调模型、Goal 与 SDK 分别开启恢复链 |

现有 Query 控制器已经能在主模型首调失败时程序化接管。[S07] 最小工作是让该路径使用统一的资格/故障域/预算判断，确保尚未形成计划时也有原 turn 身份与真实错误可追溯；不是另造第二个 LLM 执行 owner。

难度分类不是硬依赖：明确低复杂度或已有冻结工作包可跳过；只有分类结果可能改变合格路由时才调用。首版若仍保留现有分类器，则先观测其延迟占比，不无依据承诺去掉它必然更快。并行发两个付费模型做同一初始判断不是默认优化。

## 六、执行依赖图、验收返工和持续推进

方案以稳定 task ID 表达 DAG。初版依赖边只采用“前置当前成果已验收”一种语义；不要同时引入 start-to-start 等复杂依赖。每次原生派发工作包前，检查它属于当前计划 revision、前置验收仍有效、资源不冲突、权限和预算未变；模型的调度建议不替代程序准入。

资源可以是文件/目录、同一数据库测试范围、浏览器会话、部署目标或共享构建锁。文件边界只是最低要求：不同文件也可能修改同一服务；未隔离的写资源按 exclusive 串行。Runtime 不能证明逐包 gate 时，采用主 Agent 串行执行，不宣传其具有强制可控并行。

### 状态转换表

以下是原状态的产品投影及转换要求，不新增一份平行状态机数据库。任务节点尽量复用已有 pending/running/awaiting_review/completed/rework/failed/interrupted/blocked/unknown。[S11]

| 当前条件/投影 | 触发及原 owner 的动作 | 后续与可见证据 |
|---|---|---|
| 评估请求 | 原 turn 记录用户输入引用，核实意图与已有权限，必要时形成步骤 | 直接回答、可执行计划，或具体待人决定；“正在理解”不计执行进度 |
| 等待人类决定 | 原方案 owner 保存精确版本/变更与缺口 | 可信确认到达后进入 ready；相同回执幂等，旧版确认无效 |
| pending/ready | 原 queue/native owner 通过依赖、资源、预算和权限 gate，提交 exact claim | 实际进入 Runtime 才显示 running；只排队显示已排队 |
| running | 工具/native event 推进原 attempt；模型仅提建议 | 文本、工具、产物和检查有各自事实；失去 live 证明显示 unknown |
| 模型恢复等待 | 原 Query 保存故障与绝对下一次时间，暂停其普通空闲计时 | 显示恢复原因/已试路线/期限；等待计数不计任务完成度 |
| native 完成 | 原执行 owner 提交真实 terminal 和产物/检查引用 | 进入 awaiting_review，不直接 completed |
| awaiting_review | 主 Agent/验证者按当前产物版本运行必要检查，由原 root 提交 review | accept 后 completed；失败进入 rework，明确未通过的条件 |
| rework | 创建同一 task 的新 attempt，给具体失败证据；受影响后续成果失效 | 重新选择执行方式/模型，保留旧 attempt；不能覆盖旧失败记录 |
| 无 ready 节点但有活跃任务/审批/恢复计时 | 等原 owner 的实际事件 | 属于等待；不能因为 DAG 暂无 ready 就误报永久阻塞 |
| 无 ready、无 active、无合法定时等待，且未完成 | 重新核对缺依赖/资源/能力/授权/同步缺口 | 明确 blocked/unknown 原因与解除条件，不空转“继续努力” |
| 所有必需节点验收通过且总体验收满足 | 原任务/Goal owner 结算，保存交付证据 | 完成；无部署范围时不制造部署阻断，有部署范围时需对应真实路径 |
| Stop/撤销/期限耗尽/无法确认副作用 | 同步关闭后续准入，精确 stop 并持久结算 | stopped/paused/blocked，按实际原因；不能变更模型绕过 |

每次完成或返工都会驱动原 Runtime 对剩余 ready 集合重新评估。模型调用结束而工作未验收，不应默默结束总体任务。跨 turn 必须选择一个原 owner，具体如下；Task、Goal 和方案不能各自续跑同一任务。[S10–S12,S16]

### 普通行动请求怎样有界持续推进

这是必须明确的产品取舍：**普通明确行动请求可以包含本次交付所需的有限接续；不能因此暗中创建一个长期 Goal。** 第一版建议扩展现有 `startSessionPlanTurn` 的队列生产者，而不是调用 `goal create` 或新建另一套执行管理器。它只生产原计划的一次后续唤醒，实际工作仍由原 Runtime 执行；不添加轮询 timer、独立任务表或另一个 DAG scheduler。

| 原工作归属 | continuation 的唯一生产者 | 方案账本的作用 |
|---|---|---|
| 普通聊天中已明确接纳的行动计划 | 现有 planStart producer，在原 SessionEngine queue/metadata CAS 内扩展为有限链 | 保存范围、授权依据、预算、当前 slot、尝试与验收 |
| 用户明确启用/已存在的 Goal | 原 SessionGoalManager/goal-orchestrator | 只保存/投影步骤和验收；不另开 planStart 续接链 |
| Task/Inbox 等已有 owner 的执行 | 原 owner 的已授权 lifecycle；本轮内优先由原 Runtime 完成 | 不凭消息 source 字符串接管；没有跨轮授权时不独自升级为 Goal/plan 自动链 |
| 纯回答、仅讨论/方案 | 无自动行动 continuation | 不为保持“活跃”制造下一轮 |

普通计划的最小实现顺序：

1. 原始行动请求在可信准入时绑定本次 plan、scope、预算和原消息；内部计划可直接 ready。首次准备仍可只有理解/只读评估，模型未产出计划前的首调故障归 Query 恢复，不新开计划 turn。
2. 沿已有 planStart 单 slot 建立 queueId/claim 并派发，给该原请求注册 `onTerminal`；回调闭包绑定精确 Session/plan revision/queueId/claim，不能只靠 terminal.text 或最后一条消息归因。[现有接口见 S16]
3. 原 terminal 到达后先结算当前 slot/usage，回读已持久化任务与 live/native 状态。只有终态明确、没有未知工具结果/在途后台工作/待审批、未停止、原范围仍授权且预算充足时，才考虑接续。可接续原因仅为存在尚需执行的 ready 工作或待主 Agent 验收；“模型说继续”不构成原因。
4. 在同一次原 metadata CAS 中记录已处理的精确 terminal，消耗父预算并把 slot 替换成下一唯一 queueId/pending。重复 terminal 或旧 callback 发现 slot 已变化即结束。新 queueId 是新一次唤醒身份，不新建冗余 generation；每次仍走原 claim、beforeDispatch 和 native 最终同步 fence。
5. 唤醒内容只引用当前计划、未完成 task/attempt 和验收证据，要求继续剩余工作；不能重发原用户整条任务或历史工具。已经完成的动作仍受原 ledger 保护。所有必需验收完成则直接结算，无下一 slot。
6. 原 native error/stopped、恢复耗尽或安全 pause **不**进入一般“未完成再来一次”的循环；沿原故障/Stop 状态停下。否则一次新 plan turn 会洗掉原模型重试上限。已证实未派发的 claim 可按原安全退回 pending，但仍不重开父预算。
7. 冷恢复先核对原 slot/native receipt；不确定的 claimed/dispatched 停为 unknown。只有可证明已结算、下一 slot 尚未派发且仍在预算内的 pending 可以恢复。写盘或对账失败不凭聊天推测下一步。

建议 P1 的**工程初始上限提案**是本次普通行动最多 3 个 native turn（首次加最多 2 次唤醒），并设置本次 run 的绝对期限/模型 token 上限，且不超过已有用户费用授权；这些上限由同一 run 预算持有，重启、换模型和 plan revision 均不重置。3 是防止隐式无限续跑的初版产品选择，**不是已实测最佳值**；实际期限/token 值须由原费用授权与实施时的明确默认规则落盘，未能形成有限预算时不启动自动跨轮。

到上限后保留成果、未验收条件和已用预算，明确本次有界执行结束且目标尚未完成；用户说“继续”只可在核对原停因后接纳下一份明确额度，不能覆盖未知副作用或原 Stop。长期无人值守/按时间持续执行才进入用户明确的 Goal/Task 能力。本方案没有要求简单任务也用满 3 轮，一轮已验收就立即结束。

这一扩展确实增加了原 plan producer 的 terminal 处理职责，必须审查其与 Goal/Task 的 owner 互斥、durable claim 及取消，不应包装成“只有提示词改动”。它复用已有计划 owner 与队列，没有新建第二个执行 owner；如果对应 Runtime 无法提供可靠 terminal/动态 gate，第一版只支持单轮或显式 Goal 的已有能力，不能假称完整持续自动执行。

连续推进不等于永不停止。合理停止条件：用户要求停；授权缺口；实际预算/期限到达；未知副作用；必需能力不可用且等待窗口耗尽；无法恢复的持久化/身份冲突；重复返工没有新增证据或策略变化。无产物时先区分“正在研究”与“无实质进展”，不要按固定工具次数或一段沉默直接判死锁。

初版可设内部有界的同原因返工/换路次数作为保险，但每次重试应有修正依据，达到界限后做诊断与具体停因，不编造失败概率，也不要求所有任务经过同样轮数。数值应由受控场景和后续真实数据确定，不能把本评审的猜测当性能基线。

## 七、持久接续、人类纠正与未知副作用

恢复读取顺序：原用户/任务授权及控制 revision → 当前计划版本与验收依据 → 原生执行 receipt/队列/后台任务 → attempt/产物与动作 ledger → 模型恢复 checkpoint。聊天最后一句和前端最后一个 loading 都不授予执行权。

| 情况 | 允许的接续 | 必须保留的边界 |
|---|---|---|
| 明确未进入 native，原 owner 已取消 claim | 在原队列重新准入同一工作包 | 原 deadline/预算不归零 |
| 进入 native 后 ACK 丢失 | 查询原 native receipt、持久历史及工具结果 | 状态是未知，不重新发送用户任务 |
| 成功动作已记账 | 从其结果继续 | 新工具 ID 不能使相同动作重新获准；同义改参仍依赖业务幂等/核对 |
| 写操作已请求，结果未知 | 原 owner 只读核对；可获得可信结果时经明确 reconcile 结算 | 核对不了则停。模型说“可能失败了”不能证明可以重做 |
| App 重启/休眠 | 仅按原 checkpoint、history、任务 owner 与控制 fence 恢复 | 进程不存在不等于旧副作用不存在；关闭 App 不承诺连续运行 |
| 用户纠正范围/验收 | 原计划 revision 更新；撤销尚未开始的受影响工作；精确处理在途任务；复验受影响产物 | 旧确认不授权扩大范围，旧验收不覆盖新内容 |
| 用户 Stop 后迟到 success | 记录为旧 attempt 的真实结果，供对账 | 不重新派发后续、不自动转为总体成功、不恢复 timer |

目前 action ledger 已有精确动作保护及保守只读核对，不能把它扩写成任意外部系统 exactly-once。[S13] 后续支持业务 reconcile 时，必须由工具/业务 owner 提供具体 action ID、对象版本或幂等键及只读证据；审阅模型不能清除 uncertain。若当前只支持 native Read/Grep/Glob，先如实停在这一能力边界，不能为了“自动恢复”放开普通 Bash/MCP。

## 八、用户看到什么，以及怎样证明真执行

沿已有聊天、执行计划、任务面板和错误提示增量呈现，保持一个执行进度来源。默认不展示所有策略内部字段，也不强迫用户维护协调者/实现者/验证者三套配置。

用户应能看到：

1. **当前理解和范围**：简短说明目标、产物和完成条件；必要时指出缺的决定。清楚授权下是进度说明，不是额外许可弹窗。
2. **真实执行状态**：排队、运行、等待模型、等待工具、待验收、返工、暂停/未知分开；完成数只计当前有效验收。
3. **模型事实**：配置选择、实际派发路线、确认接管、失败/冷却原因及发生时间；“候选”不写成“已调用成功”。上游实际模型无法验证时显示其证据边界。
4. **成果和检查**：可打开的产物、修改/版本、检查输出和验收依据；跨 Agent 贡献可追溯到 task/attempt，不能用“已安排”冒充执行。
5. **控制**：纠正目标、固定/恢复自动模型、调整已授权预算、暂停/停止、查看未知动作并选择明确对账。控制请求成功与原生终止确认应分开显示。

工程侧从现有记录投影一条因果链：真实输入/授权引用 → plan revision → task/attempt → 实际模型及 native queue/tool ID → artifact version/check output → root review → 总体 terminal。安全关联 ID、时间和固定枚举可进日志，原文/凭据不扩散到遥测；不用为了这条链创建另一个事件数据库。

应分别测量：分类耗时、排队时间、到实际首调用的时间、到首个实质工具/产物的时间、恢复等待、验收通过耗时、实际/估算费用及其来源。多 Agent 是否收益，以端到端交付时间、返工和实际支出比较，不能用调用数/并发数作成功指标。未测量前只提出指标，不给虚构提升百分比。

## 九、可观察验收场景

这些是未来实现的验收要求，本线程未运行。确定性策略、真实 SessionStore、adapter/loopback、实际组件 UI、真实 Provider/原生客户端与业务验收分层记录；前一层不能替代后一层。

| 场景 | 可操作输入/注入 | 必须观察到的结果 |
|---|---|---|
| A01 纯问答 | 问课程结构优劣 | 正常回答/必要只读查询；无建站写入、无无关任务/收费咨询 |
| A02 明确制作 | “把给定课程做成可本地打开的网站”，已有材料 | 在已授权范围内直接制作；可打开文件/页面、内容对应材料、基本导航可用、检查证据；无机械方案确认 |
| A03 仅方案 | “先给建站方案，别开发” | 只有方案和必要只读检查；没有文件制作、部署或工具权限升级 |
| A04 可并行工作包 | 内容整理和隔离样式资产；随后集成依赖两者 | 有限并行且 task/attempt 明确，集成仅在前置验收后启动；共享资源冲突会串行 |
| A05 首调失败 | 协调路线在零交付时返回连接故障 | 原 lease 有限恢复并使用合格候选；原用户任务只接纳一次，无先决委派输出，无重复写计数 |
| A06 分类失败 | 分类 timeout/格式错/被 Stop | 有界回退及具体 reason；Stop 不污染长期健康；无任意增权/升价/无限调用 |
| A07 共同故障域 | 两个 alias 同网关故障，另一路不同已知域 | 说明共同故障域而非轮转名字；按统一预算选另一路或等待；耗尽后有具体停因 |
| A08 子 Agent 自报成功 | 产物缺文件或测试实际失败 | 进入待验收，检查失败后返工；旧成功不能覆盖新 attempt，未验收不计完成 |
| A09 工具/权限错误 | 错参数/拒绝权限/业务校验失败 | 定位并修正对应路径；不把 Provider 标坏，不自动换凭据或扩大权限 |
| A10 未知写入 | 可控测试工具先落一次写入后丢回包 | 原 owner 对账或停；恢复、更换模型、重启后计数保持一次；核对不了不重试 |
| A11 控制竞态 | 退避或预算预留/CAS await 中 Stop/撤销 | 后续 native entry 被拒；迟到回执不复活；停止持久化失败如实报错 |
| A12 重启及丢 ACK | plan claim/native dispatch 后模拟断进程/丢响应 | 恢复原任务/attempt/期限；未知 claim 不自动变授权；不从最后一句重发 |
| A13 总体完成 | 节点均回传，但总体验收缺可用网站/发布验收 | 保持待验收或明确未完成；HTTP 200/模型 final 无法伪造成功；只按约定范围判定 |
| A14 用户纠正 | 运行中更改一项验收，另一项保持 | 只废止/复验受影响节点与后继；旧版授权不能放大范围，未影响成果保留 |
| A15 能力/成本边界 | 图片请求候选无图片证据；价格未知；父预算不足 | 不盲切、不丢图片；标明费用未知/估算；子 Agent 不能分别取得完整父预算 |
| A16 固定与 Runtime 支持 | manual Session、DSH、外部 Codex/CC，以及旧 pending plan | 固定会话不自动换路；各 Runtime 只暴露已证明能力；旧门禁、Stop、原 owner 不被新策略绕过 |
| A17 普通请求有限续接 | 第 1 轮成功终结但待验收，第 2 轮返工，第 3 轮仍未完成；重复 terminal/中途重启；并测已有 Goal | 每个 terminal 最多生产下一 slot 一次；第 4 轮自动派发为零；预算不重置；无新 Goal/Task 行；已有 Goal 仅由 Goal owner 续跑；模型恢复 error 不借新轮绕过 |

真实 Provider 级别至少验证普通文本、工具往返、图片（如产品宣称支持）、首调失败与取消；供应商无法受控注入的故障留在 loopback 证明范围，不能标为真实故障已验证。业务写入只用获授权的测试身份/可控数据。

## 十、分期落地：先交一条完整路径，再扩展组合

### P0：已存在的局部清理，作为基础交付

保留本批统一候选池与删除独立备用设置，不追加本评审全部机制到同一补丁。当前源码层行为见 S05–S07；本线程不替主会话确认 main、CI 或生产状态。必须在发行时验证旧恢复 checkpoint 不因策略身份变化被重放。

### P1：单 Agent 的端到端最小闭环

目标是 A01/A02/A03/A05/A06/A08/A10/A11/A12/A13/A14/A16/A17 首先成立，并保持其余安全边界。范围：

- 原准备/准入流程分别产出意图建议和可信授权依据，复用 plan 内容与 turn/source 引用；清楚行动请求不增加审批。新增授权类型只能由原 owner 写入；历史 pending 保留确认门禁。
- 在同一 auto-route policy 形成要求过滤、故障类别、近期观察与共享恢复预算；仍限制当前支持的同档普通 API 接管，固定 Session 保持固定。首调恢复不需要另一个 LLM。
- 让一个原生执行者形成真实产物，当前 attempt 对应检查并记录 root review；普通计划由原 planStart producer 的有限 terminal 链推进，显式 Goal 保持原 Goal owner，分别在具体停因下结算。
- UI 复用原计划/任务/模型提示，准确区分候选、派发、待验收和完成；无新设置页或 owner。

P1 的最小演示应是“给材料 → 可本地访问的课程网站 → 检查内容/导航/适配 → 保存成果和验收 → 重启能看到相同成果”，中途注入一次首调失败和一次验收失败。这个演示可不启用多 Agent，仍然证明自动执行闭环。公网部署不是该演示的暗含步骤。

### P2：把原任务依赖变成可执行准入，接入有价值的协作

目标：A04/A07/A15，并对 P1 全量关键回归。给原 plan step 增量补充验收、requirements 和资源边界；由既有 native gate/queue 验证 ready 与资源占用。原 Runtime 拥有执行/子 Agent 生命周期，Host 只做既有授权与准入/投影。

不同模型先通过现有无工具咨询参与分析/审阅，接入同一候选资格、父预算、停止及证据语义；已有用户明确池共享授权时不逐次问，无共享授权则精确说明发送范围再等决定。咨询不假装执行者。跨 Provider 有工具执行只在精确每步身份、取消、history、账本及费用证据验证后开放。

### P3：依据真实结果改进能力档案和策略

在不额外默认收费的前提下，用真实已授权调用的成功/失败、延迟、检查与返工数据调整排序；补足各 Runtime 已证明的能力矩阵。能力升级可以扩展为同一策略的更适合路线，不新增独立“备用”或“多 Agent 总开关”。不把自动化推到未获授权的外部动作。

## 十一、明确未知与关键反证

- **线上状态未知**：本线程只查指定源码，不证明 519.2、冻结候选或任意日常客户端已经有这些机制；也不证明真实 Provider 已恢复。
- **上游模型身份与能力未知**：RC 等路由标签、模型 ID、目录 tier 和价格不能证明实际模型版本或完成该任务的能力；本评审不点名推荐未经测试的模型组合。
- **故障域相关性不完整**：本次连接故障不足以判定模型本身坏、网关坏或公共网络坏；自动策略应保留原因级别与不确定性。
- **跨 Provider 工具协作未证明**：当前 SDK agents 的 model 参数不等于可自由更换任意 Provider；文本外援不具备文件/工具执行证据。
- **完全语义化权限不现实**：普通 shell 或自定义工具不能仅靠自然语言 scope 自动可靠判定全部副作用；未知动作仍用现有权限/测试身份/只读核对，不承诺通用 exactly-once。
- **长期自治的效果未知**：更多模型/并行/推理投入可能增加延迟、冲突与费用；P1 应先用单 Agent 形成可验收交付，再验证协作收益。
- **多阶段不等于缺授权**：步骤多可以有内部计划；只有新的决定或真实权限缺口需要人类。相反，简单的一次发送/支付也可能必须确认。
- **不产出不等于该并行**：分类延迟、恢复等待、工具卡住、审批、缺材料、只读研究与模型反复读取要区分；不能通过启动更多调用掩盖原因。

## 十二、交叉质询后的收敛

主会话转交的实现审计指出：普通行动任务不能被静默转换为 Goal，现有 planStart 只做一次启动，没有完成后自动续接。本线程已用 S16 核实接口和调用点，并修正原先“跨 turn 一律交 Goal”的不完整表述。

收敛后的最小方案是：普通计划由原 planStart producer 在原 SessionEngine queue/turn owner 中接入有界 terminal continuation；已有显式 Goal 则仅由 GoalManager 继续，二者互斥。仍复用原方案/任务账本、metadata CAS、控制 fence 与父预算，不新增 store/scheduler；原模型恢复 error 不借下一轮重置额度，未知派发或副作用先对账。

“自动计划的原请求授权”也不等于 human confirmation：新增类型只能由可信入口/原 owner 绑定来源与 scope 写入，不能让模型伪造用户确认。上述连续推进和授权类型均是后续实现建议，当前局部候选池清理不包含这些能力。
