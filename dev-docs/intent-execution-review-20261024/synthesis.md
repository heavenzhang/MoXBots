# MoXBots 多模型与意图驱动自动执行：综合评审

状态：两线程报告与交叉质询已完成，主会话综合裁决；后续机制为实施建议，尚未实现。任务 MOXBOTS-INTENT-EXECUTION-20261024。

## 判断

当前存在自动模型路由、可调用子Agent工具、方案/任务/验收账本以及显式Goal的自主接续能力，但不能把这些部件等同于“基于用户意图自动完成目标”。最明显的问题是：普通行动请求未保证进入有验收条件的工作流，模型回答结束与目标完成之间缺少统一闭合判断。首调故障已有程序级推理接管，不能将“没有子Agent启动”误写成“没有程序接管”；但推理接管不提供任务图和业务验收。

两线程报告：[架构方案](architecture.md)、[独立审计](audit.md)；评审过程与验收场景见 [执行记录](coordination.md)。

已直接核查：`src/shared/autoRoute.ts` 分类提示词只定义easy/ordinary/hard三档；`src/shared/sessionPlanConfirmation.ts:46` 的requiresSessionPlan仅有定义与测试调用，未接入生产请求。方案启动、普通轮次、Goal和Query恢复仍分别由现有owner负责。本评审不把这些owner合并为一个新执行器。

## 统一机制的职责

| 环节 | 需要决定什么 | 应由谁负责 |
|---|---|---|
| 理解请求 | 问答、讨论、立即行动、未来触发；目标、产物、约束、验收条件 | 模型提取建议，原输入和持久账本保留依据 |
| 核对授权 | 现有授权是否足够，是否出现新增外部后果或必须补问的缺口 | 原Session/Task/Goal owner确定性核对，不由分类标签授权 |
| 形成执行图 | 是否需要拆分、依赖、文件/资源归属、单agent或并行 | 原方案/任务账本记事实，原执行owner派发 |
| 选择模型 | 对每个工作包匹配能力、上下文、协议、已知健康、故障域、预算 | 一份统一候选策略；配置就绪不等于真实可用 |
| 持续推进 | 当前下一步是否可执行、是否等待、失败是改路还是返工 | 原队列/执行owner根据账本和真实终态转换 |
| 验收收口 | 产物是否满足标准，证据是否齐全，哪些验收仍未知 | 主Agent核验；确定性状态机只接受与任务/尝试对应的验收事实 |

## 模型组合

模型角色随工作包而定，不固定绑定某个厂商或模型名称。简单问答和机械检查可直接用合适的低成本模型/确定工具；跨模块设计和复杂诊断需要有相应能力的协调者；可独立实现的工作包才能并行；重要结果安排非实现者审阅。并行度受依赖、独占文件、运行资源和预算约束，不以开满agent为目标。

候选池是唯一模型入口。初选、连接失败后的同档候选、验收失败后的能力调整、暂时冷却均由同一策略决定，不再维护独立备用名单。模型ID、价格和强档标签不能作为能力证明；多个provider/model指向同一个服务地址时可能共享故障域，需要优先考虑可验证的路由差异。网络不可用、工具参数错、权限不足和结果质量差应进入不同处理路径。

## 明确行动请求怎样直接执行

用户说“把课程体系做成网站”，已经授权在约定范围内进行制作；可以形成内部计划并开始。不得要求用户为了开启自动执行重复确认同一意图。若用户说“先讨论方案”，则只能讨论；若出现付费、新公网暴露、扩大权限、对外发送或破坏性写入，则按实际授权等待。

内部自动计划的启动依据必须明确指向原用户请求和原执行owner；它与需要真人审阅的proposal有不同授权来源。不能伪造真人点击/确认回执，也不能把“做网站”一律转换成无限Goal。普通会话采用有界的本次任务推进：完成、Stop、必要人类输入、预算耗尽或未知副作用时停止。

## 需要补齐的闭环

收到请求 → 判断意图与完成条件 → 核对授权 → 形成/更新内部任务图 → 选择执行方式和模型 → 派发就绪工作包 → 核验结果 → 未达标返工或继续下一步 → 验收通过后完成。

故障发生在这条链的任何位置，都应回到原owner管理的等待/重选/返工状态，而不是创建一个绕过原状态的新会话。协调模型首调失败且零输出时，可在原Query安全预算内选择兼容候选，不能要求失败的模型先调用Agent工具。子Agent自报完成、工具返回成功和模型final都不自动等于用户任务完成。

## 必须保留的边界

- Stop/撤销和必要审批优先；不能借换模型、换agent或重建Session绕过。
- 已完成动作保留；未知写入结果先只读核对，不能盲目重试。
- 数据与执行身份仍归原Session/Task/Goal/Query/ledger；不新建第二套任务数据库或后台调度平台。
- 当前功能、模拟验证、真实Provider、原生安装和生产验收分别报告。
- 只把确实无法继续的原因交给用户；普通可逆选择、已有授权和独立准备由系统继续推进。

## 最小实施顺序

1. 消除当前确定冲突：移除独立备用策略，统一同档候选。本分支已实现并通过局部验证，未合主干/发布。
2. 接通普通行动请求与原方案账本，区分内部已授权计划和待真人确认的proposal，明确完成标准及时间/调用/继续次数上限；所有后续步骤在同一授权和共享预算内。
3. 在原SessionEngine terminal和原queue接入任务/尝试绑定、终态后的验收或有界续跑。普通制作请求不偷偷创建Goal；已有显式Goal继续由原GoalManager管理。先把一条单Agent端到端路径验收，再接入依赖与独占资源约束的并行。
4. 在相同预算约束下，统一候选策略补足实际健康/故障域、有限候选尝试和角色能力匹配，避免反复撞同一个失效路由；原生有工具子Agent与跨Provider文本咨询必须区分，当前未证明任意跨Provider可写worker均可接管。
5. 用coordination.md的13个场景验收整链，再验证真实Provider与真实用户产物。不能只验收分类、截图或子任务创建。

## 两线程交叉质询与主会话裁决

架构线程强调复用原owner、避免再造平台；审计线程证明难度分类并非意图执行决策、requiresSessionPlan未接入生产、普通turn终态未联动未验收任务。主会话独立核对requiresSessionPlan搜索结果、turn-lifecycle普通completion及review准入，并接受审计的首调接管反证。

主要分歧是普通任务跨turn是否必须使用Goal。主会话裁决：普通已授权行动在原SessionEngine terminal/原queue内进行有稳定身份、停止门禁和共享上限的有界推进；继续意图先在原metadata CAS持久化，再由原queue幂等认领，每个后续turn重新正常准入，不能复用已终结推理lease；显式长期Goal仍归原GoalManager。既不偷开无限Goal，也不新增外层循环或第二任务数据库。内部自动计划需要原admission owner出具来源依据，不能让模型自填“已授权”或伪造真人确认proof。

最终验收引用具体工具结果、产物版本与当前attempt；文本evidence和主Agent自报本身不能证明所有必需验收通过。机器可验证项先验证，业务判断无法自动完成时如实保留待验收，不能假造通过。
