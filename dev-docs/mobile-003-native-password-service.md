# Native password adapter: service boundary

The optional service setting `native_password_login` defaults to `false`. It enables `POST /auth/login/password` for the existing Dex local-password account authority. It does not create accounts, import password hashes, read Dex storage, create a public client, bypass MFA, or enable any Dex grant. Browser OIDC remains unchanged.

Request JSON is closed camelCase `{deviceId, pkceChallenge, username, password, consentAccepted:true}`. `consentAccepted` is required on every attempt: missing, null or a non-boolean value is rejected during decoding; `false` is explicitly rejected before rate admission, provider authentication or creation of a Ready transaction. It has no default or remembered-approval shortcut. Both decoding and false-value rejection return closed `invalid_request` errors with `Cache-Control: no-store`, without reflecting the sensitive request body. The existing service body bound is 8 KiB; canonical UUID and original S256 challenge checks apply. Username is limited to 512 UTF-8 bytes and password to 1024, both nonempty without NUL. Password is not trimmed. Passwords and account inputs are not logged or persisted by this adapter. A client should clear the password from UI memory after submission and never retain/replay it automatically.

## Proposed native confirmation (not approved for production)

For each attempt, the native page must start with an unchecked confirmation and let the person explicitly agree to provide their account identifier, name and email (`openid profile email`) to the same MoXBots confidential client for login. Only that action may submit `consentAccepted:true`; no startup, refresh, retained checkbox or automatic retry may synthesize consent. The flag is this request's explicit client assertion, not a server attestation of a visual interaction.

This is a proposed replacement of the Dex webpage's confirmation for this single client, not preservation or creation of a Dex consent record. The production owner reports that the current Dex configuration explicitly has `oauth2.skipApprovalScreen:false`, so omitting the old confirmation would change the current policy. The service guard makes the native confirmation requirement reviewable, but does **not** authorize that policy change or enable production. Explicit human release authorization for this replacement remains required. `native_password_login` stays disabled until that authorization and the deployment prerequisites are satisfied; this code does not change `skipApprovalScreen`.

The service alone authenticates its existing confidential Dex client against the operator-controlled discovered HTTPS token endpoint, using password grant, scopes `openid profile email` and a random server nonce. No redirect or alternate endpoint is accepted. It requests no offline-access scope. The original verifier checks ID-token signature, issuer, audience, expiry and nonce; the existing bounded JWKS rotation path is retained. Raw provider errors and tokens are never returned. A successful verification creates an original `Ready` transaction and returns only `{transactionId, expiresAt}`. The original PKCE poll consumes it once, issues the original AuthStore session and preserves the same `(issuer, sub)` principal, network and session TTL. Original cancel/expiry semantics apply. Lost responses may leave a transaction until its existing bounded expiry; they do not authorize automatic password replay.

Fixed per-process limits: four in-flight password verifications, 60 attempts per fixed 60-second global window and five per-account attempts per 60 seconds. All admitted attempts count independently of provider result/account existence. Account buckets contain only process-salted SHA-256 keys of trimmed, lowercased account names, expire after the window, and have a 1024-entry hard cap. Limits are per instance and reset on restart; a multi-instance rollout requires an additional shared perimeter limit, not a claim that these counters are distributed. No request-supplied proxy/IP header is trusted for identity.

Closed route errors are `401 {error:{code:"OWNED_CREDENTIALS_INVALID"}}` for unknown account or wrong password, `503 ...OWNED_PASSWORD_LOGIN_UNAVAILABLE` for disabled/unsupported/provider-verification failures, and `429 ...OWNED_PASSWORD_LOGIN_RATE_LIMITED` for rate or concurrency limits. All carry `Cache-Control: no-store`. Existing other-route error formats are unchanged. Provider configuration errors and credentials errors are deliberately not conflated into a successful login.

## Deployment prerequisites (not performed)

The committed bootstrap pins Dex `v2.46.0`, enables its existing local password database and uses the private `myagents-agentnet` client. Its generated `oauth2` settings **do not** set `passwordConnector`, so the committed default is not a working password-grant deployment. Running production configuration/version has not been inspected by this implementation task. Before enabling the service flag, review the actual private Dex config and metadata, existing client, user IDs and issuer against the source owner. Enable the local password connector/grant only in that reviewed configuration; preserve all existing authorization-code grants and original storage/keys/user IDs. Do not rerun bootstrap, which generates a new user ID/client secret and would change authority. Never move the client secret into the mobile app.

If MFA, external IdP policy or another login restriction applies, leave this adapter disabled for that scope; password grant must not bypass that policy. An existing requirement for Dex webpage confirmation also keeps this adapter disabled unless a human explicitly authorizes the single-client native confirmation replacement described above. This feature is limited to already-existing local-password accounts approved for direct password authentication. No production config, service restart, real credential submission or deployment is part of this code change.

Sources reviewed: [Dex password connector](https://dexidp.io/docs/connectors/local/), [Dex OAuth2 grant configuration](https://dexidp.io/docs/configuration/oauth2/), and [the pinned v2.46.0 implementation](https://github.com/dexidp/dex/blob/v2.46.0/server/grants/password.go), which requires client authentication and passes the supplied nonce into token authorization.

## Verification scope

Service tests use synthetic credentials and signed mock-provider tokens. They cover required true consent (missing/false yield zero provider calls, zero Ready transactions and no rate admission; true verifies the mock provider before creating one Ready transaction), HTTP closed rejection of missing/false/null/string consent, default-off/closed request limits, signature/issuer/audience/nonce/expiry rejection, bounded JWKS rotation, unchanged principal/network, PKCE one-time consumption, cancellation/expiry, non-enumerating public failures, and concurrency/account/global limits. These are local service tests, not evidence of a human approving the release, a Dex consent record, production password-grant enablement, a real account signing in, or a physical phone completing login.

## Isolated real Dex acceptance

Run `bash services/agentnet/scripts/test-native-password-dex.sh` on a Linux host with its local Unix Docker engine and the existing CI toolchain. The existing owned-service workflow explicitly executes this step. It uses the official Dexv2.46.0 image by its inspected immutable image ID, records binary version and repository digest, binds only127.0.0.1, and creates a private synthetic account/client and temporary CA-only HTTPS fixture. No production files, credentials, remote Docker context or relaxed certificate/signature verification are used. Cleanup removes only its own container and temporary directory.

The ignored opt-in Rust case exercises real TLS discovery/JWKS/password token, nonce/issuer/audience/signature checks, original handler/PKCE poll one-time consumption, wrong password, cancellation and test-only advancement of the local transaction deadline. Its same-subject principal baseline comes from an independently verified real password-grant token through the original AuthStore, not a real browser authorization-code flow or production account. Local compilation and synthetic tests are not a substitute for the explicit CI run. Actual production same-account/principal/network comparison and physical login remain the sole release owner's coordinated acceptance gates.
