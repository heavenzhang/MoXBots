# Builtin API context recovery

Owner: existing builtin Query token, bridge, SessionStore and Rust SessionGoalManager. Task: MOXBOTS-CONTEXT-RECOVERY-20261017.

## Capacity and compaction

An API provider's model `contextLength` is declared capacity, not evidence that every upstream route accepts that size. Non-managed third-party API-key routes default to a 200,000-token operational compaction budget, capped by a smaller declared window. A model row's explicit `contextCompactionWindow` can raise/lower this budget; it never raises declared capacity. Native model aliases still derive `[1m]` from declared capability. The SDK compaction window and UI denominator share the operational policy. The UI identifies operational budgets separately. Official Anthropic, subscription/managed endpoint and cloud-scoped authority retain their existing policy.

## Inference-only repair

Only explicit context-overflow responses (400/413/422) trigger one reduced inference retry. Generic HTTP400 pauses the Goal as an invalid request. Before retry, SessionStore commits the complete request into a private, content-addressed, immutable archive. Reduction preserves every system instruction, user text, tool name/input/ID, paired result ID and latest two messages. Only older bulky assistant text/tool evidence is excerpted with archive references and hashes. Internal SDK system messages are preserved. Unknown block shapes, missing/uncertain tool pairs, inadequate reduction, background work, concurrent inference, stale tokens and cancellation stop automatic repair. Native histories are never rewritten and queue turns are never replayed.

SSE delivery remains admitted until message_stop. Partial streams seal the request against implicit replay. Native /compact success creates the SDK's own compact_boundary. Its explicit compact_result=failed overrides an outer SDK success result. Structured failure codes pass through the JS terminal outcome to Rust; Rust pauses the same Goal, preserving objective/progress and explicit resume, instead of ten identical retries ending in a terminal blocked Goal.

## Action protection and persistence

Once repair is armed, a Query-level ledger keys replay protection by tool name plus canonical JSON input. Native outcome settlement additionally requires the identity of the exact admitted execution; the action hash alone cannot settle an invocation. Known successful actions are denied with prior evidence; Read/Grep/Glob remain repeatable. Every newly allowed business action first reserves an uncertain entry durably, then commits a matching native result from PostToolUse. A native success means the tool returned successfully; it is not acceptance of downstream business work. A crash or failure between these commits leaves an uncertain action that must be checked read-only before that operation is repeated; independent operations remain available through ordinary permission checks. Ledger commits serialize within the controller and validate the current Product/native-history owner in SessionStore. A new Query restores the same-history ledger, including after native compaction has removed old tool pairs. Corruption, write failure and ledger capacity exhaustion fail closed. An immutable same-history armed marker also makes a missing ledger fail closed.

Private files: `<app-data>/context-recovery/<product-session>/`: SHA256 request JSON and `ledger-<native-session>.json`, directory0700/files0600. Ledger<=16MiB/2048 distinct actions; immutable archives<=128 and256MiB total, each<=64MiB. Limits stop automatic recovery without deleting evidence. Existing Product/native transcripts remain authoritative; archives are operational evidence, never source-controlled. Different native histories use distinct ledgers.

This is exact tool/input replay protection, not distributed exactly-once delivery: semantically equivalent operations with changed arguments require business-system idempotency keys and receipts. A tool must report its real success/failure; an ambiguous result is never proof of success. Downgrading to an older binary that lacks these gates requires pausing affected Goals and preserving/exporting their checkpoints first. Do not let the old version automatically continue recovered business work.

## Recording outcomes while recovery is unavailable

An exact live native tool admission remains the authority for its result even while background work revokes automatic inference recovery. Native error receipts require the same Query/Session owner, scope, emitted tool ID, input hash and pending admission; they do not require `canRecover`. Stop, stale ownership, missing evidence, timeout/signal exits, historical unknowns, concurrent identical admissions and failed persistence remain protected. Recording the result does not grant retries, failover or stream continuation; those entry points retain their existing background and deadline gates.

For historical triage, `node --import tsx/esm scripts/inspect-recovery-ledger.ts --ledger FILE --native-history FILE` reads explicit, consistent private snapshots. It verifies the envelope digest and production ledger schema, then emits bounded redacted per-action leads without commands, result text or custom tool names. Physical native history is not proof of the selected branch or business outcome: success/error records, duplicate native IDs and missing evidence all remain diagnostic. The command never writes a ledger, dispatches a tool, restores a Query, or authorizes execution. Keep the report and source snapshots private; do not commit business histories. The report is preparation for evidence-based reconciliation, not a historical repair endpoint.

## Settled background stream continuation

Task MOXBOTS-SETTLED-STREAM-CONTINUE-20261021 adds a narrow result-boundary path through the existing SameTurnStreamContinuation and SessionModelRecovery. It neither replays an HTTP request nor creates another queue, waiter, recovery owner or budget. The original root/native Session/route/Goal remain unchanged; a one-use marker in the last native user input retires all old-root fingerprints and opens a distinct inference namespace. Completed action hashes remain denied.

Admission requires the original live Query, an armed clean durable ledger, no active request, a stable manifest of every admitted request in that scope, and zero tool bytes possibly delivered by every interrupted request. Delivery evidence is recorded before enqueue: malformed/unknown SSE, prefilled message content, orphan argument deltas, conflicting indices/IDs, unfinished or invalid arguments cannot grant a receipt. Tools from completed streams must match exact native tool IDs and canonical action hashes at PreToolUse and have paired PostToolUse/Failure terminals. All known background runs (including level-only observations) must have exact run identity and authoritative task_updated terminal evidence; a notification, user ACK, disappearing level or cleanup never substitutes. Current nonambient level must be empty. First version conservatively requires terminal evidence for all known task edges, so ambiguous/ambient edges without a provable run may also deny this path.

Transport cause is an internal request/attempt-local callback from the original body/timeout owner, never an HTTP header, model error string or generic rewritten SSE frame. Provider/auth/billing/policy errors, parse failures and Abort/consumer cancellation cannot arm either the new receipt or the existing foreground continuation. Raw Anthropic clean EOF without terminal and real socket/body-idle failure retain their explicit cause; Chat/Responses clean EOF requires a validated model-progress prefix and no incomplete SSE frame; parser/provider errors, ping-only and half-frame EOF remain unproven. Callback revocation follows the existing attempt and request lifecycle.

Only background work already settled when the original native result arrives is supported. If it settles later, the result is finalized under the existing protection; no hidden polling/held result is added. Terminal HTTP rejections are outside this narrow stream receipt path; an unrelated authentication/policy failure is not promoted into retry authority. Historical unknown actions, capacity exhaustion, stale manifests, Stop, owner/route changes or failed storage/CAS remain blocked, with a fixed non-secret explanation in the original conversation. Evidence is bounded independently: 4096 request/tool-delivery entries and background run observations, native action/admission evidence limited to the existing 2048-entry ledger bound, argument witness at most 1MiB. Capacity disables this new proof without evicting old safety evidence or changing ordinary tool permission.

Receipts use the existing immutable SessionStore archive writer with SHA256 of its exact JSON bytes; ledger and checkpoint writes retain the same owner and durable CAS. New checkpoints are version2/kind=stream and carry the receipt digest plus original engine authority. This proof is live-only: cold Session restoration, Goal request admission or another engine cannot reconstruct permission from a ledger/archive alone and must pause. v1 checkpoints without this proof retain their previous behavior; v2 never downgrades during wait/rebind/pause. The original consumed receipt can authorize subsequent interruptions of the same live chain while preserving its id and earliest deadline. Older 5158/e7 readers reject version2 rather than treating it as a normal waiting checkpoint during rollback. This is controlled refusal after restart, not automatic cold recovery.

Synthetic tests cover the real handler with both controllers, actual SessionStore file publication, two same-id/same-deadline namespace continuations, native SDK result/Pre/Post hook wiring, Stop across commit/adoption, Query replacement across the new await, and cold refusal. Real native/provider recovery and original business completion remain separate acceptance.

### Native operation review

The built-in Session tab exposes a redacted operation review through SessionEngine. `GET /api/session/recovery/actions` reads the validated ledger and the existing SDK history reader (5 seconds, at most 50,000 records / 200,000 content blocks). `POST /api/session/recovery/reconcile` requires the existing Rust P256 user-action signature over the exact body, path, Session ID and request time; CLI tokens and model-origin HTTP requests cannot create this authority. The response never includes commands, tool inputs, results, bridge tokens or custom tool names.

The query-only settlement contract is `builtin-task-query-reviewed`: exact native `TaskList {}` or `TaskGet {taskId: string}` (also `{}`, which fails native parameter validation). Extra fields and other tools are rejected. This contract establishes query-only semantics, **not successful completion**. It does not parse Shell/SQL commands, trust `is_error` text, accept a later success as an old mutation receipt, or assert that physical history is a verified selected chain. The original action hash binds the fixed built-in name and complete canonical input; namespaced MCP tools do not qualify.

A second contract, `native-pre-tool-denied-reviewed`, establishes **non-execution of exact old calls**, never business success. SDK-selected messages must match raw records read through the SDK's memory-only import collector. Each matching action requires a unique tool identity, root Session identity, exact use/result UUID linkage, matching canonical messages and input hash, `is_error: true`, and structured `permission-rule` / hook rejection metadata. Text-only hook errors, ordinary shell failure, sidechains, duplicate identities and any unproven same-action peer stay protected. Reads are bounded by the SDK-reported 64 MiB source size, collector bytes/records and the existing review timeout; oversized/truncated sources cannot establish absence of side effects.

`preToolDenials` appends bounded audit receipts while preserving raw uncertain hashes. The existing operation journal discharges only the proven legacy lead. Old native tool IDs cannot run again; a deliberate new turn may admit the same command under a new ID, and any later uncertain attempt blocks independently. Current-turn fences, Stop and retry authority are not reset. Self-owned PreToolUse denials are durably recorded before returning deny so future history does not invent uncertain execution.

The signed recovery action also repairs verified old product error flags through the existing ProductTranscriptContent writer. All targets must uniquely match tool ID, name and full normalized input hash before any update. Only `isError` metadata is appended and flushed; text, timing and tool-end events are preserved. New SDK user tool results propagate their typed error flag to product history and live events.

The idle Session UI performs a bounded read-only inspection and exposes one restore action for eligible records. Mutations run sequentially against each returned ledger digest; close, Session changes and stale epochs stop further requests. Ambiguous responses are inspected, never blindly reposted. Unsupported operations remain visible and protected. A completed review permits a subsequent explicit message in the same Session; it does not send that message or replay previous tools.

Review uses the existing Session mutation lock and updater admission. It requires no active/queued turn, prewarm, background task, MCP mutation or model retry waiting state; a partial rewind or pending conversation mutation also blocks it. Session/native identity, Stop epoch, Query generation, bridge/controller binding and workspace are captured and rechecked across IO. The existing controller persistence tail drains before review. SessionStore compares the expected ledger digest under its existing file lock and repeats the live guard before atomic rename.

`readonlyTasks` is an optional version-1 ledger field containing bounded identity-scoped audit receipts. The raw `uncertain` hashes remain serialized. A current controller excludes only validated receipt hashes from effective uncertainty; the live adoption updates only that subset and never resets request guards, retry fences, recovery budgets, paused model state or the current turn’s strict per-operation replay protection. Historical analysis recognizes only those reviewed exact query hashes. Older binaries ignore the new field and conservatively retain the original unknowns; they may discard the receipts on a later save, requiring review again after upgrade. Corrupt receipts fail closed.

No review starts inference or business work. A missing native use, ambiguous tool ID, unsupported tool, changed owner/digest, storage failure or unsigned request stays protected. A response lost after commit is checked by refreshing the persisted review; it must not be treated as proof that the original task succeeded. A stale live controller after a failed post-commit adoption remains conservative until its native lifecycle reloads the ledger. General business-operation receipts and cross-restart automatic continuation are separate, unfinished capabilities.

### Per-attempt native outcome journal

Task MB-RELIABILITY-20261028 phase three adds optional `operationAttempts` to the existing version-1 ledger. The existing controller and SessionStore remain its owners. Each native admission gets an independent UUID and retains Product/native Session, Query generation plus a fresh bind epoch, scope, tool-use ID, canonical action hash and reservation time. The native PreToolUse hook can reserve a background invocation without a foreground bridge emission; absence of that emission still prevents stream-continuation proof. A background-only reservation uses a Query-epoch scope label for storage while its live guard still compares the actual optional scope.

PostToolUse and PostToolUseFailure may settle only the pending admission with that exact owner, bind epoch, tool ID, input and scope, rechecked across persistence. A terminal entry records result digest and time, with `returned/success`, `returned/bash-exit` or `unresolved/error`. An interrupted/unknown failure stays unresolved; a duplicate or late callback cannot promote it to success. Concurrent identical actions remain separate: one return cannot clear a peer reservation or a legacy unknown. Generic/history result recording cannot discharge an existing unknown by action hash. The exact native Bash error proof still requires its existing emitted-tool witness.

The detailed journal is bounded at 2048 attempts. When full, only a returned receipt from an older Query with the same Product/native Session owner can be compacted into a durable SHA-256 tool-identity tombstone. Reserved, unresolved and current-Query entries are never compacted. This avoids a permanent 2048-success Session lifetime limit while retaining duplicate-identity denial. Compaction removes the older receipt's detailed journal fields; original transcripts and existing action evidence are not changed. Tombstones are never evicted and are separately bounded at 65536; that bound, a full protected/current Query, or the Store's 16 MiB limit fails closed. Capacity messages direct the user to inspect the Session; a new Session is only for independent work, never a replay of unknown actions.

Uncompacted journals retain schema1. A compacted journal uses schema2 with owner-bound unique tombstone hashes, rejecting foreign owners, live-ID overlap or corruption. Journal-aware schema1 readers reject schema2 instead of silently discarding the identity fences. Older rollback readers that omit the journal extension retain raw unresolved hashes and existing successful-action fences; they cannot grant native receipt authority. Restore validates identities, statuses and coverage against raw unknown hashes. No cold reader can use an archived native receipt as live Query authority. Reservation or result persistence failure blocks subsequent mutations; the last durable pending entry survives restart. Missing/foreign success, Stop, changed scope/owner and callback reuse never consume another attempt. Query-only reviews keep their prior constrained contract.

`inspectActionLedger()` exposes only attempt/action IDs, status/outcome and timestamps, without commands, inputs, outputs or custom tool names. These are execution observations, not new task owners, business receipts, reconciliation authority or an automatic restart executor. Original uncertain business operations still need external evidence before any reconciliation. Validation and release boundaries: `dev-docs/reliability-20261028/phase-three.md`.

原生回调不能匹配当前有效准入时，诊断记录 `commit_unmatched`，与 `commit_complete`、`commit_failed` 分开。它只解释回调未结清原因，不授予新操作或历史结清权限；仍只保留工具/动作摘要。

## Operation-scoped verification (MB-REPLAY-SCOPE-20261031)

Independently of the optional model-recovery toggle and streaming mode, an explicitly admitted, healthy inference with identifiable historical unknowns uses the full native history and strict per-operation action protection. It no longer enables a tool-name whitelist that excludes all Bash calls. Unknown exact tool/input hashes and previously successful hashes remain denied; a distinct SSH log/status check or an independent next step can be reserved and executed through the existing PreToolUse/permission policies. Every such Bash call remains journaled before dispatch. No shell text is classified as harmless, no permission mode is widened, and no ledger entry is erased. Same-scope cancelled/failed requests, stale ownership, corrupt/unidentifiable history, failed persistence and ledger capacity still stop execution.

A missing result with a complete, unique tool use can be scoped to that operation for ordinary inference. It remains invalid for automatic context reduction, inference retry, failover or stream continuation. Duplicate IDs, orphan results and malformed history cannot be scoped safely. Restored projected histories with unknown operations may use the original full body for this explicit verification path; they are not reduced or automatically retried. If the body still exceeds the provider window, context recovery remains blocked pending reconciliation.

Verification results are evidence for deciding the next authorized step, not automatic settlement of the old unknown. A successful native Bash return (including a background launcher’s exit code 0) does not establish downstream build/package/deployment success. Check the actual task output/log and artifact before dependent work. Continue polling background output through native Read and the SDK’s task output file; do not relaunch the original build. A repeated exact Bash command remains subject to the same replay protection; do not vary arguments to evade it. Semantically equivalent operations and business dependency correctness still require existing task policy, business idempotency and receipts; the hash guard does not claim semantic equivalence detection.

The persisted schema is unchanged. Strict protection (`streamArmedOnly=false`) survives a cold Query and preserves original unknown/completed entries. An older binary will conservatively restore its former whole-turn restriction; rollback does not silently replay protected operations. Task-query and proven-no-dispatch reviews retain their own owner/CAS authority. UI has no new switch or blanket-disable option.

Validation includes `context-recovery-scoped.unit.test.ts`, the bridge integration suite and `scripts/verify-operation-scoped-recovery-loopback.ts`. The latter runs real SDK hooks and native Bash against a synthetic local log/model: old unknown launch count 0, package count 1, two duplicate denials and cold ledger restoration. It does not certify a production SSH account, installed signed client or production business completion.
