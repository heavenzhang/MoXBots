# Persistent model availability recovery

Task: MOXBOTS-MODEL-RECOVERY-001. Owners remain the builtin Query/bridge, SessionStore, and (for Goal controls) Rust SessionGoalManager.

## Scope and waiting

Ordinary builtin API Sessions and Goal turns use the same inference lease. Existing primary short retries and authorized backup selection precede durable recovery. A long Retry-After bypasses short repeated calls to that provider. Recovery retries inference only: it never resends the original task, rewinds native history, or creates a second Goal/Task queue.

SessionStore persists `modelRecovery` with a random chain ID, exact Product/native history/turn identity, optional Goal ID, non-secret route hash (including backup selection), wait count, absolute next attempt, deadline, HTTP status and waiting/paused state. The default window is 30 minutes with 15s..5min backoff; a longer upstream Retry-After is honored, or recovery pauses when it cannot fit the remaining window. Disk latency is deducted from the wait. Every post-wait dispatch rechecks deadline, cancellation, Query/route/root and checkpoint authority. SDK, bridge and Goal retries cannot each reset that window.

`SessionModelRecovery` is Query-scoped policy and scheduling, not a new persistence writer. Before a wait can authorize another inference, ContextRecoveryController archives the full inference and commits completed action evidence through the original private SessionStore ledger. Availability recovery activates action protection without reducing context. Exact tool name/canonical JSON input successes cannot repeat under a new native tool ID. Uncertain writes, corrupt/missing armed ledgers and storage errors fail closed. Semantically equivalent writes with different arguments still require business-side idempotency and read-only reconciliation; this is not distributed exactly-once delivery.

## Controls and terminal evidence

Pause/Stop synchronously revoke the local epoch and request binding before awaiting storage; the original exact SDK interrupt is sent immediately. SessionStore serializes checkpoint CAS by history, chain ID, status, turn, attempt and next-attempt timestamp. It writes a private immutable `context-recovery/<product>/stopped-<chain>.json` control fence with file and directory sync before publishing paused metadata. If the sessions index rewrite fails, the fence still prevents automatic cold recovery. If even the fence cannot be persisted, Stop interrupts the Query and reports `MODEL_RECOVERY_STOP_NOT_DURABLE` instead of claiming durable success.

The API watchdog suspends inactivity accounting only during explicit recovery backoff, retaining ordinary inference/tool timeouts. Goal remains busy in the original turn, so its existing deadline, pause/cancel control revision and exact current-turn stop continue to apply. A safety stop is returned as `automatic_replay_blocked`, causing the existing Goal recovery pause rather than another generic ten-failure dispatch chain.

Only the active recovery bridge's native child receives a 35-minute `API_TIMEOUT_MS` (the recovery window plus bounded short-call overhead). Native byte/event/retry watchdogs and Bun transport idle timeout are disabled for that loopback lease. The bridge arms its 30s upstream header limit only while fast recovery is authorized; a fenced request retains the generic 300s header bound. The Session retains its ordinary 10-minute inactivity watchdog outside explicit backoff, and recovery retains its absolute 30-minute deadline. Utility/one-shot and managed routes keep their existing timers. SDK 0.3.296 source was inspected for `API_FORCE_IDLE_TIMEOUT=0` and retry-watchdog behavior; documented timer boundaries are in the [official environment-variable reference](https://code.claude.com/docs/en/env-vars) and [streaming watchdog reference](https://code.claude.com/docs/en/network-config#streaming-idle-watchdogs).

HTTP 200 is not success evidence. An SSE terminal must be delivered into the consumer queue before availability checkpoint clearing; a pre-terminal error/truncation seals that inference lease. Eligible streaming foreground turns can continue under the same original turn as described below; unsafe or canceled turns pause. A terminal-receipt cleanup tolerates the SDK closing HTTP, but retains the Query epoch/owner/checkpoint checks so user Stop wins. Following inference waits for in-flight terminal cleanup before reading the journal.

Chat Completions requires a recognized `finish_reason` before emitting `message_stop`; EOF and `[DONE]` cannot manufacture missing completion evidence. Trailing usage and a valid finish without `[DONE]` remain supported. Explicit upstream errors, unknown finish reasons and malformed Chat/Responses frames fail closed. A non-stream Chat response without a valid assistant choice/finish and a missing stream body return 502 before delivery, allowing only the existing authorized retry policy.

Recovery wrappers forward complete SSE frames, retaining incomplete byte/frame tails until another chunk arrives. On a pre-terminal error/EOF they discard the incomplete tail and deliver an `automatic_replay_blocked` protocol error. This seals the old HTTP request without retrying its partial output. Consumer cancel and explicit Stop keep their own cancellation path, including when Stop wins during an awaited checkpoint write. Non-stream upstream body reads keep the request abort listener attached until their `await` completes, so Stop can release a provider connection stalled after headers.

## Same-turn stream continuation

Task MOXBOTS-STREAM-RESUME-20261020-01 adds the same path for ordinary builtin API Sessions and Goal. Before a foreground streaming inference reaches the provider, ContextRecoveryController arms the existing durable action ledger. Prearming alone does not block intentional repeated actions in ordinary execution, or turn legacy failed/unpaired tool history into a new initial 409. Such uncertain history still cannot authorize recovery. Utility/background tasks and external/managed runtimes are excluded.

A trusted bridge stream error, malformed frame, read failure or EOF before a terminal can persist `modelRecovery.kind=stream`. It shares the existing absolute recovery deadline, backoff and original Product/native/turn/Goal identity. Once the native SDK returns its error result, SameTurnStreamContinuation wakes the existing native input generator with a one-use random continuation reminder. This input does not repeat the original user task, enter Product history as a user message, claim a second Goal turn, reset usage, or close the original output/FIFO owner.

Before the next provider call, the last native USER message must contain the exact pending capability marker; trailing SDK SYSTEM messages are allowed. Authority, deadline, durable checkpoint and complete tool-use/result pairing must all agree. Only then can ContextRecoveryController retire the settled failed namespace and ModelFailoverController start the next inference namespace. Original fingerprints remain fenced across that advance. Confirmed canonical tool-name/input successes are blocked even under new IDs; pending/failed/unpaired actions, changed owner, storage errors or competing background work pause instead of guessing. Native partial text is preserved in Product presentation, but SDK 0.3.296 may omit unfinished assistant text from its next wire history, so the application does not invent a completed native response.

The stream recovery chain is retained across subsequent successful inference/tool cycles and cleared only at the original turn's final success. Completion CAS failure produces a safety error, not a successful Product terminal. Stop immediately revokes the continuation capability and timer before its durable pause; a late persistence callback cannot resume or overwrite the stopped evidence. A stopped cold checkpoint remains stopped. Existing Goal claim, revision and deadline controls remain authoritative.

Server-owned `Message.streamRecovery` evidence is preserved by the existing transcript details codec. The collapsed quality reference reports observed interruptions, admitted continuations, protected completed actions, recovery status and elapsed observation span. Missing legacy evidence is not displayed as zero or success. This is recovery evidence, not content quality scoring or proof of business-side exactly-once delivery. Verification and remaining native/provider gates are recorded in `dev-docs/stream-continuation/acceptance.md`.

### Queued human input after Force

A desktop input retains its original ingress authority while waiting. If its predecessor is paused only after enqueue, the generator rechecks at the real admission seam, after the predecessor native terminal and the successor domain guard. It joins the existing durable pause before the original SessionStore CAS can retire that exact paused inference checkpoint; Product/native/route/checkpoint, controller, Query generation and queue cancellation must still match. The action ledger and immutable old Stop fence remain. Automatic reminders cannot perform this transition, and cancellation during the CAS leaves the old chain stopped. The normal execution and Goal guards still own task budgets.

## Cold restoration

Opening/restoring the original Session loads its native identity, exact route and original action ledger. Only a verified waiting intent can automatically enqueue a bounded continuation reminder, never the original user input or a prior tool call. The new Query rebinds that same chain and honors the original next-attempt time and deadline before any provider call; it starts with the user's selected primary route and does not reacquire a short-retry budget. A stop fence, expired window, missing native history, pending rewind/mutation, mismatched route or uncertain ledger requires explicit resolution. A new explicit user instruction can retire a paused intent through the original cancelable admission/CAS, creating a new recovery epoch.

Goal intents are excluded from ordinary cold enqueue: only the original Rust Goal owner can resume them, preserving its revision and single current-turn claim. Rust startup, Goal resume and deadline semantics are unchanged. Closing a Tab retains existing BackgroundCompletion/Goal owners. Application exit/sleep is not a promise of uninterrupted execution: ordinary persisted waits resume when the original Session is restored; Goal startup uses its existing durable owner.

External/subscription/managed/integrated runtimes keep their native inference and credential ownership. This bridge does not intercept those processes or replay their tools; this release establishes the recovery contract for builtin API execution in both product modes. Real Provider, signed native installation and production business acceptance remain separate release gates.

### Explicit read-only reconciliation

A stopped native tool can leave a durable write-ahead reservation without a committed outcome. A subsequent ordinary, unprojected inference may inspect that same history even when the restored ledger is already in strict protection mode. Streaming prearm retains completed archives, uncertain actions and the existing protection mode, persists through SessionStore, and rechecks the original turn/background authority before dispatch. During that turn, only the existing native `Read`, `Grep` and `Glob` tools may run; Bash, MCP tools, completed actions and unrelated business writes remain blocked. Neither model text nor a successful read clears uncertainty or authorizes replay.

This exception does not admit automatic availability recovery, same-turn stream continuation, a restored context projection, corrupt ledgers, stale owners or canceled requests. Inference retry and failover remain fenced. Local archive, persistence and owner failures return their bounded owner-authored reason rather than being mislabeled as model transport failures; arbitrary thrown text is never forwarded.

### Settled native errors

A normal Bash process failure is distinct from an unknown tool outcome. The original live Query can settle its own reservation only when the SDK `PostToolUseFailure` pairs with the exact streamed native ID, canonical input and pending admission, explicitly reports `is_interrupt=false`, and returns the native `Exit code N` prefix for a normal nonzero exit below 128 (excluding timeout code 124). MCP errors, missing receipts, signals, cancellation, another pending admission of the same command and older uncertain actions retain their existing fence. A failed command can have made partial changes; its receipt never certifies rollback or permits its automatic replay during recovery. The model must inspect the preserved output and use a corrected command.

The same controller records its own `PreToolUse` denial as not dispatched. These proofs are private, bounded `nativeErrors` entries in the existing SessionStore ledger, scoped by Product/native history, Query generation, turn, native ID and action hash. Bash receipts additionally bind the exact error-result digest. Subsequent native history must pair with that receipt; merely printing an exit code or the guard marker grants no authority. Denial proofs never remove an older uncertain entry. Persistence failure or a changed settlement owner fails closed. The common 2048-entry cap and settled-interruption digest include these proofs.

Existing ledgers without such receipts are not automatically cleared or upgraded from error text. Their native history and action evidence must be preserved and reconciled through the original owner. This fix prevents new poisoning; publication alone does not establish that a previously blocked business Session has recovered.

## Verification

Focused bridge/Session owner tests cover storage and control races, Retry-After, canceled/expired re-admission, partial SSE, and success cleanup. SessionStore integration uses actual private archives/ledger/index and forces index publication failure after Stop. Builtin execution integration checks stop during explicit resume CAS and refuses missing native history. UI uses the production MessageList/GoalStatusBar with synthetic state transitions.

`node --import tsx/esm scripts/verify-model-recovery-loopback.ts` runs SDK 0.3.296/native child with isolated HOME, synthetic loopback providers and an actual MCP counter. It verifies completed counter=1 through 503 recovery and a same-native Query reconstruction while two new-ID duplicate calls are denied. The controlled fixture clock compresses recorded 15s waits; the script's fixture writer is not claimed as production SessionStore/native UI acceptance. Evidence and final CI/main/publisher receipts: `dev-docs/model-recovery/acceptance.md`.

## Repeated HTTP rejection evidence

A fully received non-success HTTP response is rejection evidence, not successful assistant delivery. After existing bridge retry/recovery policy settles, QueryRequestGuard can retain that response for the exact scope/fingerprint and return it when the native SDK repeats the input. The repeated response keeps the original HTTP status and cause but carries automatic_replay_blocked in its code/message, preserving the existing Goal/Session safety terminal instead of letting an outer scheduler redispatch a spent inference. This does not grant admission, contact a provider or replenish a retry budget. Each error body is bounded to16KiB/1s and each guard snapshot budget to1MiB; admission evidence is never evicted to make room. In-flight and cross-scope lookups return no evidence. A blocked scope may read only its own fenced terminal error; it still cannot acquire any inference/action admission. A declined/exhausted durable owner seals the lease and retains its original known HTTP rejection with the same safety terminal. Partial successful streams, cancellation and unknown error bodies never grant replay. The bridge logs final HTTP status without request/error bodies so a subsequent generic safety error cannot hide the first known rejection.

## Repeated native fault verification

The explicit `scripts/verify-reliability-matrix.mjs --out /absolute/new/directory --rounds 10` runner checks ten native SDK scenarios serially and preserves source/log hashes, full receipts and first-failure evidence. Stream and cold fixtures bind exact SDK session UUID, Query generation and native tool-use ID. Two consecutive stream failures must share the original deadline; Stop at the second wait must prevent further dispatch. The 100/100 result and synthetic-provider, compressed-clock, fixture-writer/Goal limitations are documented in [phase five](../../dev-docs/reliability-20261028/phase-five.md). It is an explicit local test, not part of default CI or evidence of installed/real-provider acceptance.
